การตั้งค่า PHP / php-fpm / nginx / MySQL (เหมือนกันทุกแอป)
  • php.ini: opcache.enable=1, validate_timestamps=0, memory 256MB, jit=disable
  • php-fpm: pm=static, max_children=16 (เท่ากันทุกแอป), max_requests=0, clear_env=no
  • nginx: fastcgi upstream keepalive=32 + fastcgi_keep_conn on, gzip off, access_log off
  • MySQL 8.4: innodb_buffer_pool=2G, skip-name-resolve · ข้อมูล world 10,000 แถว seed แบบ deterministic (mt_srand(42)) + fortune 12 แถว

7วิธีวัด & ข้อจำกัดที่ควรรู้ก่อนตีความ

  • สถานการณ์ 5 แบบ: plaintext (framework overhead), json (serialization), db (query 1 แถว), queries×20 (prepared stmt ใช้ซ้ำ), fortunes (template + HTML escaping + UTF-8 รวมแถวภาษาไทยและแถวที่ต้อง escape <script>)
  • Verify ก่อนวัดเสมอ: 30 endpoint (6 แอป × 5 สถานการณ์) ต้องผ่าน contract — สถานะ 200, content-type ถูก, รูปร่างข้อมูลถูก และ fortunes HTML ต้อง byte-identical ข้ามทุกเฟรมเวิร์ก จึงเริ่มวัด (พิสูจน์ว่าทุกแอปทำงานเหมือนกันจริง)
  • Interleave: วนสลับ run→scenario→app ทั้ง 5 รัน เพื่อให้สภาพเครื่อง (thermal/cache/background) กระทบทุกเฟรมเวิร์กเท่ากัน + warmup 8 วินาทีต่อแอปก่อนวัด
  • Production config: ทุกเฟรมเวิร์กรันโหมด production พร้อม cache config/route/view (Laravel, Symfony, CI4) และไม่มีเฟรมเวิร์กไหนเริ่ม session — route ของ Laravel สมัครนอก web middleware group เพราะ load client ไม่ส่ง cookie (มิฉะนั้นจะกลายเป็นวัดการสร้าง session file ใหม่ทุก request)
ข้อจำกัด
  • นี่คือ micro-benchmark ของ overhead ต่อ request ไม่ใช่ "แอปจริงบนเฟรมเวิร์กไหนเร็วกว่า" — แอปจริงมี cache, queue, external API ที่ทำให้สัดส่วนต่างเล็กลง
  • ไม่ได้วัด ORM/Query Builder ของแต่ละค่าย (ใช้ raw PDO เท่ากันหมดโดยตั้งใจ)
  • ตัวเลข RPS เปรียบเทียบได้เฉพาะในเครื่องเดียวกัน/รันเดียวกัน — เครื่องอื่นให้ดูอัตราส่วน % เทียบ PHP เปล่า
  • เฟรมเวิร์กที่ช้ากว่ามักแลกมาด้วยฟีเจอร์ที่ครบกว่า (validation, ORM, ecosystem) — benchmark วัดต้นทุนต่อ request ไม่ได้ตัดสินว่าเฟรมเวิร์กไหน "ดีกว่า"
